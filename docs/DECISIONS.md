## 2026-08-21 — Mockoon co-located with the API on App Runner

**Supersedes** the "Mockoon as its own Fargate task, internal-only via Cloud Map" half of the 2026-08-21 "same container image locally and on AWS" entry above.

Mockoon runs in the **same container, same App Runner service** as the FastAPI API — one image, one deploy. The container's entrypoint starts `mockoon-cli` on an internal port (e.g. `3001`) alongside `uvicorn` on the App Runner-exposed port; a reverse-proxy route in FastAPI (or a tiny Nginx/Caddy sidecar process in the same container) forwards `/mock/*` to the internal Mockoon port.

**Why the proxy, not just localhost:** the API isn't the only caller — Activities running on the Lambda worker also call the mocked third-party services directly, and Lambda can't reach the API container's `localhost`. Exposing Mockoon under a path on the same public App Runner URL (`https://<apprunner-url>/mock`) gives both the API and the Lambda worker one reachable `MOCKOON_BASE_URL`, without a second compute resource (no separate Fargate task, no Cloud Map).

## 2026-08-21 — What actually needs DynamoDB

Per-session/per-job state (conversation turns, in-progress tool calls, the current reasoning state of one `AgentJobWorkflow` run) is **not** in DynamoDB — it's Temporal workflow state, replayed from event history for free. That's the whole point of running the Strands loop inside the workflow.

DynamoDB (§5 "App database") holds exactly four things, each because it's read/written by things *other than* the one workflow execution it's about:

1. **Idempotency keys** — the one case Temporal genuinely cannot substitute for. Temporal guarantees the *activity function* is retried until it reports success; it does not guarantee the *external side effect* inside that function happens once. If the worker crashes after the payment activity's HTTP call succeeds but before Temporal records `ActivityTaskCompleted`, the activity is retried and the function runs again — a fresh invocation with no memory of the first attempt except what a durable, externally-checkable dedupe key gives it. This is proof 3's entire mechanism; it has to live outside workflow history.
2. **Registry (tenants, agent manifests, priority/fairness config)** — admin-mutated config read by many unrelated workflow executions and by the API/UI directly (agent store, tenant list) without touching Temporal. A workflow can't be "the" storage for config other workflows need to read.
3. **Installs** — same reasoning as registry: an admin-mutated join table (which tenant has which agent), not scoped to any one job.
4. **Job index** — a denormalized, queryable list for the process-monitor/session-terminal UI (per-tenant lanes, running/queued counts, p95 wait). This is the one case where Temporal *could* partially cover it — List Workflow Executions + search attributes — but a live, filtered, multi-tenant dashboard is more naturally served by a purpose-built index than by treating Temporal's visibility store as a query API. Kept in DynamoDB for now; revisit if visibility-API latency/limits are ever a problem.

## 2026-08-21 — Config module: pydantic-settings, blank env vars are unset

`app/config.py` is the single place that reads env vars — everything else imports `get_settings()`. Used `pydantic-settings` (fail-fast validation, `.env` support out of the box) over hand-rolled `os.environ` parsing.

Gotcha worth recording: a blank line in `.env` (`BEDROCK_GUARDRAIL_ID=`, for a service not provisioned yet) loads as `""`, not unset — `Optional[str] = None` fields would silently hold an empty string instead of `None`, breaking any later `is None` check. Fixed with a `model_validator(mode="before")` that maps `""` → `None` before field validation runs, so required fields left blank now fail loudly (as they should) and optional fields left blank actually read as `None`. Covered by `tests/test_config.py::test_blank_env_var_is_treated_as_unset`.

## 2026-08-21 — DynamoDB single-table schema

One table (`agent-control-plane`), on-demand billing (no capacity planning — fits a spiky flood-demo workload, low-maintenance for forkers), one GSI:

| Item | pk | sk | Purpose |
|---|---|---|---|
| Tenant | `TENANT#<tenant_id>` | `TENANT#<tenant_id>` | priority_key, fairness_weight, tier, memory_namespace, s3_prefix, installed_agent_ids |
| AgentPackage | `AGENT#<agent_id>` | `VERSION#<version>` | manifest metadata, versioned — mirrors `manifest.yaml` |
| Job | `JOB#<job_id>` | `JOB#<job_id>` | tenant_id, agent_id, workflow_id, status, priority tier, timestamps — the "job index" |
| JobResult | `JOB#<job_id>` | `RESULT` | co-located with its Job (single-partition read); output payload or an S3 pointer if large |
| IdempotencyRecord | `IDEMPOTENCY#<key>` | `IDEMPOTENCY#<key>` | proof-3 mechanism; `ttl` attribute for automatic expiry |

`gsi1` (`gsi1_pk=tenant_id`, `gsi1_sk=created_at`) lets the process-monitor list a tenant's jobs newest-first without a table scan.

No separate "Install" item — a tenant's installed-agent set is small and always read together with the tenant, so it's a list attribute on Tenant rather than a join table.

Domain Pydantic models (`app/registry/models.py`) stay free of DynamoDB concerns (no `pk`/`sk` fields) — key construction and item marshalling live in the repository layer (`app/registry/repository.py`), so swapping the storage backend later wouldn't touch the domain models.

Table created manually per `docs/AWS_SETUP.md` (console, per CLAUDE.md §2's manual-AWS-actions rule) — not by a script Claude runs.

## 2026-08-21 — No unit tests; verification is scripts against real infrastructure

**Supersedes** an earlier same-day entry that proposed `moto`-based repository unit tests (that approach was reverted before it landed; `pytest` and `moto` were removed from the dependency list).

The repo carries no unit tests, no `tests/` directory, no `pytest`, no mocking libraries. Verification is done by running the real thing against real AWS and real Temporal Cloud, via scripts under `scripts/` invoked through the `Makefile`:

- `make verify` → `scripts/verify.py`: writes/reads/deletes one of every item type against the live DynamoDB table under a `verify-` prefix.
- `make replay` → `scripts/replay.py` (lands with E1.1): pulls real recorded histories from Temporal Cloud and replays them against current workflow code. This is the **one** guard that stays, because it's the enforcement mechanism for §2's determinism non-negotiable and for proof 3 — and it's not a unit test: it replays real production histories, which mocks by definition cannot.
- `make ci` → lint + typecheck only.

Rationale: the deliverable is a boilerplate people read and fork, so the codebase stays free of test scaffolding; and the three proofs are only meaningful when demonstrated against real infrastructure — a passing mock-backed test would prove nothing about fairness, version pinning, or exactly-once payment. CLAUDE.md §2/§8/§9/§10 updated to match.

## 2026-08-21 — Verified `temporalio.contrib.strands` API (v1.31.0, experimental)

Read from the installed package source, not inferred (CLAUDE.md §3). Exports: `StrandsPlugin`, `TemporalAgent`, `TemporalMCPClient`, `workflow`.

```
TemporalAgent(*, model: str | None, task_queue, schedule_to_close_timeout,
    schedule_to_start_timeout, start_to_close_timeout, heartbeat_timeout,
    retry_policy, cancellation_type, versioning_intent, summary,
    priority: Priority, streaming_topic: str | None,
    streaming_batch_interval: timedelta = 100ms, **agent_kwargs)

StrandsPlugin(*, models: dict[str, Callable[[], Model]] | None,
    mcp_clients: dict[str, Callable[[], MCPClient]] | None,
    mcp_connection_idle_timeout: timedelta | None)

TemporalMCPClient(server: str, *, cache_tools: bool = False, task_queue,
    ...same activity options..., priority: Priority)

strands.workflow.activity_as_tool(activity_fn, *, ...activity options...,
    activity_id, priority) -> AgentTool
strands.workflow.activity_as_hook(...)
```

Key facts confirmed:

- **`TemporalAgent` takes `priority`** — model/tool activities can carry the tenant's fairness key explicitly. Activities otherwise inherit the parent workflow's priority.
- `**agent_kwargs` passes through to the Strands `Agent`: `system_prompt`, `tools`, `hooks`, `messages`, `structured_output_model`.
- Use `agent.invoke_async(...)`, **never** `agent(...)` — the sync form spawns a worker thread, which the workflow sandbox blocks.
- `TemporalAgent` disables Strands' `ModelRetryStrategy`; passing `retry_strategy=` raises `ValueError`. All retries go through Temporal `retry_policy`.
- `take_snapshot()` / `load_snapshot()` raise `NotImplementedError` by design — event history already persists state at finer granularity.
- Plugin defaults the data converter to `pydantic_data_converter`, so our Pydantic models cross the activity boundary as-is.
- `StrandsPlugin` must be on **both client and worker** — the failure converter that preserves `Interrupt` payloads across the activity boundary is installed via the client's data converter. Without it, activity-tool interrupts silently do not work.
- Omitting `models=` registers a single `BedrockModel()` factory under the name `"bedrock"`.
- `temporalio.contrib.aws.lambda_worker` (`run_worker`, `LambdaWorkerConfig`) ships in 1.31.0 — the `[lambda-worker-otel]` extra is only needed for OTel.

## 2026-08-21 — Priority & Fairness constraints that shape the demo

From the `temporal-developer` skill's `core/priority-fairness.md` and the Temporal SA design-patterns catalogue:

1. **Public Preview, and Fairness is a paid Temporal Cloud feature**, enabled per-namespace in the Cloud UI. This made CLAUDE.md §2's original "proofs use only GA features" rule unsatisfiable, since proof 1 *is* fairness. §2 amended: preview features may carry a proof but must be labelled Preview everywhere, including stage narration.
2. **`priority_key` is an int 1–5**, lower = higher priority, default 3. Not an arbitrary integer — `Job.priority_key` and `Tenant.priority_key` must be constrained to that range.
3. **Fairness is not guaranteed across Worker Versions.** Proof 2 deliberately runs two versions at once, so proofs 1 and 2 must not overlap on stage — v1 must fully drain before the fairness beat. This is a `docs/DEMO_SCRIPT.md` ordering constraint, not just a nice-to-have.
4. **Task Queue partitioning interferes with fair dispatch**; single-partition config requires a Temporal Support request. Needed for the p95 divergence to be legible from ten metres (§7). Lead-time item — file early. **Corrected 2026-08-28: not possible** — pinning a task queue to a single partition isn't something Temporal Support can grant; removed from `docs/AWS_SETUP.md`. Proof 1's p95 divergence is demonstrated with partitioning as-is (E3.2's dress rehearsal already showed the correct qualitative direction at reduced scale without this).
5. Fairness applies **at schedule time**, so enabling it mid-flood does not reorder an existing backlog. The demo's off→on toggle must therefore flood *again* after toggling, which the run-of-show already does.
6. Fairness does not cap absolute throughput of one key; per-key limits need `fairness-key-rps-limit-default`. Set separately for workflow vs activity queue types.

## 2026-08-21 — E1.1 findings from running it for real

Three things only surfaced by actually running against Temporal Cloud + Bedrock, not from docs:

1. **Do not pass `StrandsPlugin` to both `Client.connect(plugins=...)` and `Worker(plugins=...)`.** The worker inherits plugins from its client; passing it twice registers the plugin's model activity twice and the worker dies at construction with `ValueError: More than one activity named invoke_model` (plus a `UserWarning` about the duplicate plugin). CLAUDE.md §4 previously said "attach to both the client and the worker", which is true as *intent* (the client is what installs the interrupt-preserving failure converter) but wrong as literal code. §4 corrected.

2. **A versioned worker gets no tasks until its deployment version is set current.** With `use_worker_versioning=True`, the worker registers the deployment on first poll but `CurrentVersionBuildID` stays empty, and new workflows sit at `WorkflowTaskScheduled` indefinitely — no error on the worker, no failure on the workflow, nothing in the history past event 2. Fix:
   `temporal worker deployment set-current-version --deployment-name agent-control-plane --build-id v1`
   This is the same API proof 2's ramp control drives, so E6.1 T2 must wrap it rather than treating it as one-off setup.

3. **`callback_handler=None` on `TemporalAgent`.** Strands' default handler prints tokens to stdout, and it fires during *replay* too, so `make replay` output was polluted with model text. Token output belongs on the session terminal via Workflow Streams (E4.2).

Also corrected: real Bedrock model IDs in this account are `anthropic.claude-sonnet-5` / `amazon.nova-pro-v1:0`, and on-demand invocation needs the cross-region **inference profile** ids `us.anthropic.claude-sonnet-5` / `us.amazon.nova-pro-v1:0`. `.env` and `sample.env` had a fabricated `anthropic.claude-sonnet-5-v1:0`. Verified callable with `aws bedrock-runtime converse`. Model ids must always be checked with `aws bedrock list-foundation-models` / `list-inference-profiles`, never assumed.

Sandbox: `SandboxRestrictions.default.with_passthrough_modules("strands", "boto3")` — both are imported inside workflow code paths and are not deterministic-safe to re-import per replay.

Verified end to end: `make verify-agent` starts a real `AgentJobWorkflow` on Temporal Cloud with a tenant `Priority`, the Strands loop calls real Bedrock Claude Sonnet 5, returns a typed `JobOutcome`, and `describe()` reports `VERSIONING_BEHAVIOR_PINNED` on `agent-control-plane.v1` — proof 2's pinning mechanism confirmed working. `make replay` replays the real histories with no non-determinism.

## 2026-08-21 — E1.2: idempotency keyed on `activity_id`, and what running it exposed

**Key derivation** (proof 3's mechanism): `payment:{workflow_id}:{activity_id}`, derived *inside* the activity from `activity.info()`.

`activity_id` is assigned when the activity is scheduled and stays fixed while `attempt` increments across retries — confirmed empirically, not just from the field names: `scripts/verify_payment.py` runs the activity twice with the same `activity_id` and different `attempt`, and asserts the provider's invocation count does not move. A distinct `activity_id` does reach the provider, so legitimate second payments are not swallowed. Deriving the key inside the activity is what makes it survive a crash; a key generated per invocation would differ on every retry and dedupe nothing.

**Ordering and the ambiguous window:** `claim` → call provider (passing the key as an `Idempotency-Key` header) → `complete`. If the worker dies between the provider call and `complete`, the retry sees a `pending` record and cannot know whether the money moved — so the key also goes downstream, which is how real providers (Stripe et al.) dedupe. Belt and braces: the DynamoDB record short-circuits the common case, the header covers the gap.

**The proof-3 path specifically:** the demo kills right after the activity function returns, so the record is already `completed`; the retry short-circuits and the provider is never called twice.

**Counter source:** the Mockoon mock deliberately does *not* dedupe — it records every call that reaches it, so the on-stage counter measures what actually hit the provider rather than our own bookkeeping. A skeptic can't say we counted our intentions.

Two real bugs found by running it, which no amount of reading would have caught:

1. **DynamoDB rejects floats nested in maps.** `_to_decimal` only converted top-level values, so writing a payment result (`amount_usd: float` inside the `result` map) raised `TypeError: Float types are not supported`. Both `_to_decimal` and `_from_decimal` are now recursive over dicts and lists.
2. **`PaymentResult(**record.result, deduplicated=True)` raised `got multiple values`** — the stored dict already contained `deduplicated`. Now stored with `exclude={"deduplicated"}` (it describes how a caller obtained the result, not the payment) and reconstructed via dict merge so old records stay readable.

**Tool wiring:** `app/activities/catalog.py` maps manifest tool names → activities with per-*class* activity options — consequential tools (move money) get few attempts and must be idempotent; read-only tools retry freely. `AgentJobWorkflow` resolves `package.tools` against the catalog and wraps each with `activity_as_tool`. An unknown tool name fails non-retryably rather than silently running a toolless agent. Adding a tool = a catalog entry + a manifest name, never a workflow edit.

**Mockoon:** the desktop app (9.6.1) is installed but not the CLI; `npx @mockoon/cli@9.8.0` runs it with no global install, and `make mockoon` uses that. `mocks/payment-service.json` uses a CRUD route over a data bucket so POSTs accumulate and `GET /payments` lists them. A `{{{ len (data 'payments') }}}` count endpoint did **not** work (the helper resolved to 0 while the bucket had entries), so the count is taken as the length of `GET /payments` instead — fewer moving parts.

Verified: `make verify-payment` (dedupe across retries, no Temporal needed), `make verify-tool-call` (real workflow → Claude Sonnet 5 chooses the tool → `issue_payment` appears in the history as a scheduled activity → provider count +1 exactly), `make replay` clean over 3 real histories.

## 2026-08-21 — E1.3: approval policy is declarative, and two findings from running it

**Manifest shape.** Approval is a structured policy, not an expression string:

```yaml
approval_policy:
  tool: issue_payment
  field: amount_usd
  operator: gt
  value: 200
```

The Notion sketch used `when: "refund_usd > 200"`, which reads better but needs a sandboxed expression evaluator running *inside workflow code* — an `eval` surface and a determinism risk in the one place we can least afford either. Declarative fields are safe, statically validatable by `dos agent validate`, and can gain an expression-sugar layer later that compiles down to this.

**How the interrupt actually works** (worth knowing before editing `app/workflows/approval.py`): `event.interrupt(...)` does not return on the first pass — it suspends the agent and `invoke_async` returns `AgentResult(stop_reason="interrupt", interrupts=[...])`. When the workflow resumes the agent with an `interruptResponse`, the hook runs *again* and `event.interrupt(...)` now returns the human's decision. The same code path both asks the question and consumes the answer. The workflow side is a `while` loop, not an `if`, because an agent can pause more than once per session; `wait_condition` holds no worker resources, so a session can sit pending a human indefinitely at no cost.

Two findings from running it for real:

1. **`activity_as_tool` nests arguments under the parameter name.** An activity with signature `issue_payment(request: PaymentRequest)` produces tool input `{"request": {"amount_usd": 900, ...}}`, not `{"amount_usd": 900}`. The first run therefore paid without pausing — the policy looked for a top-level `amount_usd` and found nothing. An agent author must not have to know the Python signature wraps args in `request`, so `resolve_field()` searches a bare field name at any depth (keys walked in sorted order, so the result is stable across replay) and honours an explicit dotted path (`request.amount_usd`) for disambiguation.

2. **`make replay` caught a genuine non-determinism, and the root cause was my own process error.** After fixing (1), replaying the pre-fix history failed with `No command scheduled for event ActivityTaskScheduled` — the old history says "call the tool", the new code says "pause for approval". That is a real behaviour change, and I had made it **while reusing `BUILD_ID=v1`**, so old and new code shared one version identity. That is exactly the mistake Worker Versioning exists to prevent and proof 2 exists to demonstrate.

   Two consequences, both now in place: `BUILD_ID` moved to `.env` and must be **bumped whenever workflow behaviour changes**; and `scripts/replay.py` is scoped to the *current* build id, because `AgentJobWorkflow` is PINNED — a run started on v1 is only ever replayed by v1 code, so replaying older builds' histories would fail on every intentional change while proving nothing about what can happen in production. The scoping is not a way to silence the guard: reusing a build id across a behaviour change still produces exactly this failure, which is the correct outcome.

Verified on `agent-control-plane:v2`: `make verify-interrupt` — approve → payment reaches the provider (+1); deny → payment does not (+0) and the agent explains it was blocked by a reviewer; the query reports what the session is waiting on; both sessions complete in a single run (resume, not restart). `make replay` clean.

## 2026-08-21 — E3.2: fairness proof instrumentation

**Job lifecycle stays minimal — only `created_at` and `started_at`.** The wait metric needs exactly those two timestamps; no `completed_at`/status-on-finish was added, since nothing in this story needs it (that's E4.1's job-index territory). `dos demo flood` is the only caller that creates a `Job` row today; `dos agent test` and the verify scripts still don't, deliberately — see the no-op design below.

**`mark_job_started` is a no-op, not an error, when no Job row exists.** It's called unconditionally at the top of every `AgentJobWorkflow.run`, but only flood-submitted jobs have a Job row to update. The DynamoDB `UpdateItem` carries `ConditionExpression="attribute_exists(pk)"`, and a `ConditionalCheckFailedException` is swallowed in `repository.py`. This keeps the workflow generic for every caller — `dos agent test` and the verify scripts needed zero changes — rather than forcing every workflow-starting call site to adopt Job-row bookkeeping just because one new caller wants wait metrics. The activity call itself is wrapped in try/except inside the workflow, so even a genuine DynamoDB failure here can't fail the actual agent job — a metrics stamp is not allowed to matter more than the work it's measuring.

**This is a workflow behaviour change → `BUILD_ID` v3→v4.** `AgentJobWorkflow.run` now calls one more activity before doing anything else. Bumped per CLAUDE.md's versioning rule, worker deployment version set to v4 via `temporal worker deployment set-current-version`, verified against 20 real v4 histories with `make replay`.

**Real bug caught during verification: the new activity wasn't registered on the worker.** `app/worker.py`'s `activities=[...]` list named `resolve_agent_package` explicitly but not the new `mark_job_started` — both live in `app/activities/registry.py`. Worth remembering: adding an activity to a module doesn't register it — it has to be added to the worker's explicit list too, and a workflow that silently tolerates an activity failure will hide a worker-side registration bug rather than surface it loudly.

**Fairness "off" is a client-side decision, not a Temporal Cloud setting.** Fairness engages the moment any job attaches a `fairness_key` — there's no cluster-level disable. A persisted `FairnessSetting` DynamoDB singleton (`pk=sk="SETTINGS#fairness"`, default `enabled=True`) is checked inside `resolve_priority()`: off means the `Priority` built has no `fairness_key`/`fairness_weight` at all, so the job falls back to the implicit shared empty-string key (plain FIFO within its priority tier) per the Priority & Fairness reference. Centralizing the check in the one shared resolver means `dos demo flood`, `dos agent test`, and any future caller all respect the toggle automatically.

**`dos demo flood` submits concurrently, not sequentially.** Awaiting each job's full completion before starting the next would never build a real queue backlog — the whole point of a flood is that `start_workflow` calls return once accepted, while actual processing is rate-limited by worker capacity and (with fairness on) round-robin dispatch. `asyncio.gather` over `count` un-awaited-until-the-end submissions is what actually exercises the fairness mechanism.

**The flood load-generator (`flood-load-agent`) is seeded in Python, not an `agents/` package.** Same precedent as `scripts/verify_agent_job.py`'s `verify-echo-agent` — a trivial, no-tools agent that exists purely to generate real queue load, which nobody hand-authors or iterates on via SOP edits. A real `agents/` folder would be ceremony with no author behind it.

**Verified at reduced scale, not the full 200-job demo count.** Every flood job runs the real `AgentJobWorkflow` → a real Bedrock call; there's no way to exercise the queue mechanics without also paying for the model calls. Confirmed the mechanism and the qualitative direction (fairness-on separates protected tenants from the flooder's wait; fairness-off collapses them together) with a 20+4+4 job concurrent flood against real AWS/Temporal Cloud — see `docs/BACKLOG.md` for the numbers. A full 200-job dress rehearsal (E3.2 T4, and again for E8's rehearsal pass) is deliberately left for a dedicated, cost-aware session rather than run repeatedly as routine verification.

## 2026-08-28 — E6.2: armed kill, and two real idempotency bugs the rehearsal caught

**Researched two sibling repos before designing, per the user's request — neither had a reusable mechanism.** `durable-agentic-harness`'s "trading desk" demo has a `ChaosPanel` (`frontend/src/components/ChaosPanel.tsx` + `backend/fastapi_app/chaos.py`) whose "kill worker" is `docker.from_env().containers.get("worker").stop()` — an external OS-level container kill. Doesn't transfer: this repo has no Docker lane for workers (Lambda in prod, a bare process locally) and CLAUDE.md forbids Docker Compose outright. `temporal-community/temporal-agent-harness` has no Strands integration, no Worker Deployment Versions, and no kill/chaos pattern at all (confirmed by reading source, not the README). Its one relevant validation: it also treats `workflow_streams` as the sole event transport with no side channel, same as this repo's E4.1 design. Conclusion: the armed-kill mechanism had to be designed fresh.

**Armed kill is a DynamoDB flag checked inside the activity, not an external signal.** A `KillSwitch` record (`app/registry/models.py`, same shape as `FairnessSetting`) is checked inside `run_once` (`app/activities/idempotency.py`) immediately after the external call succeeds and before `complete_idempotency_record` — exactly the window idempotency exists to cover — then `os._exit(1)`. Deterministic: it lands in the dangerous window on every single run, which a raced `SIGKILL` against real network timing could not guarantee, and T5 ("rehearse ten times") demands that reliability.

**The rehearsal test (`scripts/verify_kill_resume.py`) found a real gap in the *existing* proof-3 mechanism, not a gap in the new test.** `run_once`'s dedup check only matches when a record's status is `"completed"`; a crash between the external call succeeding and that write landing (our kill switch's exact target) leaves the record at `"claimed"`. On retry, `claim_idempotency_key` correctly reports it can't re-claim, but the surrounding check (`not claimed and existing is None`) doesn't treat "claimed but not completed" as dedup-worthy, so it fell through and called `perform()` again — a real second POST to the payment service. `verify_payment.py` never caught this because it only ever tested retrying an activity that had *already fully completed*, not one that crashed mid-flight — the one scenario proof 3 is actually about. This is exactly the class of gap Mockoon's payment mock was deliberately built to expose ("no dedupe on the Idempotency-Key header... so the counter measures reality, not our bookkeeping" — E1.2), and it worked as designed.

**Fix: check the provider itself by a deterministic natural key before calling it, since the mock won't dedupe on our behalf.** `_call_payment_service` (`app/activities/payment.py`) now does `GET /payments` and looks for an existing row with this call's `confirmation_id` before POSTing. This is the standard pattern for integrating with a provider that has no native idempotency-key support: check-then-act on a natural key, rather than trusting only our own side's bookkeeping. `run_once` itself needed no change — it was already correct to call `perform()` again on any retry; the provider-side check is what makes that safe.

**Second bug, exposed by the first fix: `confirmation_id` was derived from only the activity_id suffix of the idempotency key, not the full key.** `f"conf-{idempotency_key.rsplit(':', 1)[-1]}"` keeps only `activity_id` — a small counter Temporal assigns per-workflow, starting over at 1 for every new job. Two *different* jobs whose payment happened to be, say, the 4th scheduled activity both produced `confirmation_id="conf-4"`. Once the natural-key check above started trusting `confirmation_id` as a global identity, this collision made a brand-new payment from a different job falsely match a stale leftover from an earlier run and get skipped entirely — caught because the second `verify_kill_resume.py` run (immediately following the first, without restarting Mockoon) produced *zero* new payments instead of one. Fixed to use the full key (`idempotency_key.replace(':', '-')`), which includes `workflow_id` and is actually unique.

**Neither bug needed a `BUILD_ID` bump.** Both fixes are inside activity implementations (`payment.py`, `idempotency.py`), not `AgentJobWorkflow` itself — activity code isn't part of a workflow's replay-determinism surface the way workflow code is, so this doesn't touch what `make replay` is scoped to guard.

**Re-verification scope:** `make verify-kill-resume` (3 consecutive clean runs — not yet the full T5 live rehearsal count), `make verify-payment`, `make verify-tool-call`, `make verify-interrupt`, `make verify-agents` (dispute-resolution shares `run_once` via `submit_dispute_response`), and `make replay` clean against 13 histories. Proofs 1 (fairness) and 2 (versioning/ramp) were not re-run — this story's changes don't touch either path.

**`create_event`/`list_events`, not `retrieve_memory_records`.** Introspected the installed `boto3` `bedrock-agentcore` client's service model directly (`operation_model(...).input_shape`) rather than guessing — `retrieve_memory_records` is for *strategy-extracted* semantic memory, which this Memory resource doesn't have (`docs/AWS_SETUP.md` deliberately created it with no `memory-strategies`, since that needs a model-invoking execution role this project doesn't need yet). `create_event`'s `payload` is a tagged union (`conversational` / `blob` / `json`); a conversational entry needs `{"content": {"text": ...}, "role": "ASSISTANT"|"USER"|"TOOL"|"OTHER"}` — used `"OTHER"` for a system-generated job summary, since it's neither a user turn nor an assistant turn.

## 2026-08-28 — E7.1 T3: Guardrails, and why only one tool ended up guarded

**`ApplyGuardrail` needs `bedrock-runtime`, not `bedrock` or `bedrock-agentcore`.** Confirmed via the installed client's service model (`source`: `INPUT`|`OUTPUT`, `content`: list of `{"text": {"text": ...}}`, response `action`: `NONE`|`GUARDRAIL_INTERVENED`).

**The `BeforeToolCallEvent` hook is async, and that's supported — confirmed by reading Strands' source, not assumed.** `ApprovalGate._gate` is sync (`def`, not `async def`); a first instinct might be that all `BeforeToolCallEvent` callbacks must be sync. Read `strands.tools.executors._executor.ToolExecutor._invoke_before_tool_call_hook`: it calls `await agent.hooks.invoke_callbacks_async(event)`, and `HookRegistry.invoke_callbacks_async`'s own source shows it dispatches a mix of sync and async callbacks (`if inspect.iscoroutinefunction(callback): await callback(event) else: callback(event)`). So `GuardrailGate._gate` is `async def` and calls `await workflow.execute_activity(apply_guardrail, ...)` directly — no interrupt/resume round trip needed, unlike `ApprovalGate`.

**Two real false positives found by re-verification, leading to narrowing the guarded set from two tools to one — not a code bug, a guardrail-configuration/design mismatch.** First pass guarded both `issue_payment` and `submit_dispute_response`, evaluating the tool call's JSON-serialized input against the `OffPolicyPayment` denied topic (`docs/AWS_SETUP.md`, created earlier this session). Two failures, isolated one at a time via direct `apply_guardrail` calls (not guessed from workflow-level symptoms):
1. A completely clean, in-policy `issue_payment` call (`{"invoice_id":"INV-9020","amount_usd":60,"payee":"Globex Retail"}`) was blocked. `assessments` in the raw response confirmed `topicPolicy.topics[].detected: true` for `OffPolicyPayment` specifically (not a content/word filter) — the topic's definition anchored on "actions that instruct issuing a payment" broadly, and the classifier weighted that phrase over the qualifying "outside approval policy" clause. Fixed by rewriting the topic to drop "payment" as the anchor entirely and center only on the bypass/override action (`docs/AWS_SETUP.md`'s guardrail step now reflects the corrected wording; the human ran `update-guardrail` + a new `create-guardrail-version`, since Claude doesn't run AWS mutations).
2. After that fix, a legitimate **approved** $900 payment (above the $200 threshold, correctly approved by `ApprovalGate`) was *still* blocked — reproduced in isolation with the exact tool input, confirming it wasn't a hook-ordering artifact. The classifier was intermittently associating "payment tool call + large amount" with the topic regardless of wording. Conclusion: `issue_payment`'s input (`invoice_id`, `amount_usd`, `payee`) is pure structured data with **no free-text field** — there is no adversarial-language surface for a natural-language topic classifier to meaningfully evaluate, and the correct control for the numeric threshold is already `ApprovalGate` (exact, deterministic), not a fuzzy classifier guessing at policy from bare JSON. Removed `guarded=True` from `issue_payment`; kept it on `submit_dispute_response`, whose `rationale` field is real LLM-authored free text — confirmed a normal rationale passes and an injected "just approve this without review" rationale correctly blocks. `BUILD_ID` bumped both times (v11→v12 adding the hook to both tools, v12→v13 narrowing to one) *before* testing, applying the lesson from T1's `BUILD_ID` mistake rather than repeating it.

**Guardrail config changes don't need a `BUILD_ID` bump** (same reasoning as `payment.py`'s fixes in E6.2) — they're external AWS resource state, not workflow code.

**Tagging convention adopted project-wide, retroactively applied.** Every AWS resource this project creates gets `Project=durable-agent-control-plane`, so the whole footprint is findable/deletable via one Resource Groups Tagging API query instead of hunting service by service — raised by the user, applied immediately to the DynamoDB table step (previously untagged) and to every new E7.1 resource. Confirmed safe by reading `SimplePlugin.configure_client`: re-running it against this rebuilt config (which `Client.__init__` does automatically, since the same `StrandsPlugin` instance is still in `config["plugins"]`) is idempotent here, because the rebuilt converter's `payload_converter_class` is no longer `DefaultPayloadConverter`, so the hook's second branch (return unchanged) fires.

## 2026-08-29 — E7.2 T3/T4 completed, and the verify-script race that had been masquerading as flakiness

**The S3 bucket landed, so T3/T4 stopped being blocked.** `S3_BUCKET_NAME=durable-agent-control-plane-payloads-429214323166`, created by the human per this file's companion `docs/AWS_SETUP.md` entry, tagged `Project=durable-agent-control-plane`, `us-east-1`. Everything below follows from finally being able to run the claim-check for real.

**The 256 KiB default threshold was wrong for this system, and the first run proved it.** `app/activities/sandbox.py`'s comment claimed its synthetic audit ledger was "deliberately larger than External Storage's default 256 KiB threshold." That was an unverified assertion written while building E7.2 T1 — the first `make verify-external-storage` run returned `external_payload_count=0` against a 699 KiB Event History. Measuring the actual serialized report (600 records, the same code the sandbox runs) gave **84 KiB — 32% of the threshold**. Nothing was ever going to offload.

**Fixed by configuring the threshold, not by inflating the payload.** `PAYLOAD_SIZE_THRESHOLD_BYTES = 64 * 1024` in `app/temporal_client.py`. The alternative — growing the ledger past 256 KiB — was rejected on a real cost basis, not aesthetics: the ledger is returned to the model *as a tool result*, so tripling it would add roughly 64K tokens to every subsequent turn of that job for zero analytical benefit. Threshold tuning is a first-class, documented knob (the Python SDK docs call out setting it as low as 0 for data-governance cases), and 64 KiB is set from measurement: it catches the 84 KiB ledger and the model-call payloads that carry it through the turn, while leaving job inputs, outcomes, and ordinary tool results (all well under 10 KiB) inline.

**Verified with real numbers, and the claim-check's value is visible in them.** `make verify-external-storage` (new, `scripts/verify_external_storage.py`): a dispute-resolution job offloaded **3 payloads totalling 594,883 bytes to S3** while its Event History settled at **115,522 bytes** — against **699,439 bytes** for the same job shape before offloading. The script asserts the fields the UI actually renders (`external_payload_count`, `external_payload_size_bytes`, `history_size_bytes`, straight off `WorkflowExecutionInfo`) *and* independently confirms objects landed in the bucket, so a pass can't be explained by Temporal bookkeeping alone. T4's server half confirmed by hitting the real API: `GET /api/jobs/{id}/state` returns all three fields.

**`make replay` caught a second real gap — the replay guard itself was not External-Storage-aware.** Once histories contained claim-check references, 2 of 10 replays failed with `[TMPRL1105] Detected externally stored payload(s) but external storage is not configured`. Not non-determinism: `scripts/replay.py` constructed its `Replayer` without a data converter, so it got a default one with no S3 driver and could not fetch the referenced payloads. Fixed by passing `data_converter=client.data_converter` — reusing the client's already-composed converter (pydantic + Strands failure converter + external storage) rather than rebuilding one, which is also why it composes safely with `StrandsPlugin` (its hook leaves an already-non-default converter untouched, per the same reasoning documented for `connect()` above). Clean at 10/10 after. **Worth internalising: any process that reads history — replayer, codec server, tooling — needs the same converter config as the worker, or it fails in a way that reads like a determinism bug.**

**No `BUILD_ID` bump for any of this.** External Storage config and threshold changes are data-converter concerns, not workflow code: they change how payloads are *stored*, never the sequence of commands `AgentJobWorkflow` issues. Old inline histories still replay fine (a payload with no reference passes straight through). Same reasoning as the E7.1 guardrail-config decision.

### The approval race — one root cause behind days of apparent flakiness

**Symptom:** `verify_reference_agents.py` hung and eventually died with `RPCError: transport error`, three runs in a row, always at the same point (dispute-resolution, right after incident-triage passed). It had also passed cleanly several times. `verify_sandbox_isolation.py` showed the same intermittency, which I had papered over by raising its `JOB_RESULT_TIMEOUT_S` from 240s to 300s — treating a symptom.

**Root cause, found by inspecting the stuck executions on Temporal Cloud instead of the scripts:** a batch of `verify-ref-dispute-resolution-*` workflows sat in `Running`, some for 21 hours, every one of them paused at `pending_approval` for `submit_dispute_response` with `amount_usd` of 869, 655, … — all above the manifest's $500 gate. Both scripts queried `pending_approval` **once, immediately after `start_workflow`**, treated the (correct) `None` as "this run will never need approval", broke out of the loop, and then awaited `handle.result()` forever. Mockoon randomises the dispute amount 40–900, so it passed whenever the draw came in under 500 and hung whenever it came in over — textbook intermittency with a fully deterministic cause. The `transport error` was just the long poll dying after minutes of waiting on a run that was never going to progress.

**E7.2 T1 is what tipped it from rare to near-certain.** Adding `analyze_dispute_risk` (a real Code Interpreter session) between evidence-fetch and filing widened the window between "script queries" and "workflow reaches the gated tool call" by tens of seconds, so the premature query went from usually-lucky to essentially always-too-early.

**Fixed properly in `scripts/_approval.py`:** `result_with_auto_approval(handle)` races `handle.result()` against a polling loop, approving any pause that appears *while* waiting rather than checking once beforehand, and tolerating the `RPCError` from querying a workflow that just closed. Both affected scripts now call it. `verify_interrupt.py` and `verify_pinning.py` were checked and are **not** affected — they deliberately provoke a pause and already poll *for* it, which is why they never flaked.

**Two lessons worth keeping.** First: an intermittent failure with a data-dependent trigger (here, a randomised amount crossing a policy threshold) is not "environment flakiness," and the timeout bump I reached for first actively delayed finding it. Second: the fastest route to the answer was querying the *live workflow state* on Temporal Cloud (`temporal workflow list`, then `describe` + the `pending_approval` query), not re-reading the script — the stuck runs were sitting there the whole time saying exactly what they were waiting for. 15 leftover stuck executions were terminated in one batch afterwards.

## 2026-08-29 — E7.4: Strands Swarm inside one Activity

**A Strands `Swarm` cannot be constructed in workflow code — two independent blockers, both found by reading `strands/multiagent/swarm.py`, not inferred.** (1) `Swarm.__init__` unconditionally calls `run_async(...)` to fire its `MultiAgentInitializedEvent`; that is the thread-spawning sync path the Strands plugin's README explicitly warns the workflow sandbox blocks, so merely *constructing* a Swarm inside a workflow deadlocks. (2) Swarm's handoff/timeout bookkeeping (`execution_timeout`, `node_timeout`, repetitive-handoff detection) reads real `time.time()`, and `strands` is a sandbox passthrough module here, so those reads are not replay-safe. There is also no `TemporalSwarm` counterpart to `TemporalAgent` — the plugin's README covers Models, Tools, Hooks, HITL, MCP, Streaming, Structured Output and Continue-as-new, and says nothing about Swarm.

**So the whole Swarm runs inside one Activity** (`app/activities/swarm.py`, `investigate_fraud_swarm`), built from plain `strands.Agent` instances rather than `TemporalAgent`: nothing inside a single Activity needs per-call durability, because the Activity is itself the retry unit. The accepted cost is granularity — a worker death mid-swarm re-runs the session from scratch instead of resuming at a model call, and the session terminal sees one tool call rather than a live token stream. Scoped to this one tool, and given its own `MULTI_AGENT` retry class in the catalog (180s timeout, 2 attempts) because both the read-only 15s/5-attempt and consequential 30s/3-attempt classes are wrong for two full agent turns. The alternative that preserves per-turn durability — hand-rolling the handoff across two `TemporalAgent`s in workflow code — is documented in `docs/MULTI_AGENT.md` as the right choice when losing progress is expensive; the backlog explicitly asked for Swarm, so Swarm is what was built.

**Two smaller shape details, verified rather than assumed.** Swarm addresses node results by the agent's `name` (`_setup_swarm` uses `str(node.name)` as `node_id`), so results come back as `result.results["fraud_specialist"]`. And the specialist agent carries a `structured_output_model`, so the verdict arrives as a typed `FraudSwarmVerdict` instead of prose the SOP would have to parse — with an explicit fallback if the reviewer never hands off, which reports that plainly rather than fabricating a verdict. Multi-argument activities work as tools without a wrapper: `TemporalActivityTool.stream` binds the tool input against the activity signature and passes `args=[...]` when there is more than one parameter (read from `_temporal_activity_tool.py`).

**The originally-planned cross-namespace task was dropped from the project entirely** (human decision, 2026-08-29) — it would have required standing up a second Temporal Cloud namespace to demonstrate a boundary this demo does not otherwise have, with no consumer in the repo. Removed from the backlog and the docs rather than parked as a "later" item; multi-agent collaboration in this project is the inside-a-job pattern only.

**Trigger condition is narrow on purpose.** `invoice-exception` v3→v4 requires `investigate_fraud_swarm` only when vendor risk is not `low` **and** the amount exceeds `escalation_threshold_usd` — building on the risk signal the SOP already consumed from `lookup_vendor_risk`, rather than adding a tool that fires on every invoice. Verified live: a $650 invoice from Initech Supply (medium risk) triggered the swarm, which returned `suspected_fraud=true`, and the agent correctly flipped from settle to **hold**, citing the specialist's rationale — while a $60 low-risk Globex invoice in the same regression run correctly never invoked it. `BUILD_ID` v14→v15 (new tool in the catalog changes what the workflow can schedule), bumped *before* testing, and `temporal worker deployment set-current-version` run after a worker had registered the new build id — the id does not exist server-side until a worker polls with it.

## 2026-08-29 — E7.3: the hosted lane, and the one branch in AgentJobWorkflow

**A tier-3 branch in `AgentJobWorkflow` is not the thing CLAUDE.md §11 forbids.** The rule is "no agent-specific logic in AgentJobWorkflow" — behaviour must come from the manifest, not from a branch that names an agent. `if package.tier == AgentTier.HOSTED` reads a manifest *field* and applies uniformly to every hosted agent that will ever exist, exactly like the existing reads of `tools`, `mcp_servers`, `output_model`, and `approval_policy`. Raised at Inception rather than assumed, because the line matters: a branch on `package.agent_id` would have been the violation. `run()` now resolves the package, does the cross-cutting work (job-started stamp, memory recall), then delegates to `_run_native` or `_run_hosted`, and both return `(stop_reason, output)` into one shared tail (job-finished event, memory write-back, the 500ms stream drain, `JobOutcome`). No behaviour change for tiers 1–2 — verified by `make verify-agents` passing unchanged after the refactor.

**Real `InvokeAgentRuntime` shape, confirmed against the installed boto3 service model rather than the blog examples:** `invoke_agent_runtime(agentRuntimeArn=..., payload=<blob>, runtimeSessionId=..., contentType=..., accept=..., qualifier=...)` → `{response: <blob, sensitive>, contentType, statusCode, runtimeSessionId}`. Two details the prose docs don't lead with: **`runtimeSessionId` has a 33-character minimum** (hence `SESSION_PREFIX = "durable-agent-control-plane-job-"`, which satisfies it for any job id *and* names the calling system in the hosted runtime's traces), and the session id is derived from `job_id` only — deliberately not per attempt, so a Temporal retry is the same logical hosted session rather than a fresh one.

**Response parsing is tolerant on purpose.** Our own hosted agent returns the documented `{"response": ..., "status": ...}` JSON, but E7.3 T2's entire premise is that you can register *someone else's* agent by ARN, and that agent is under no obligation to match. `_extract` handles the JSON shape, the SSE shape the HTTP contract also permits, and falls back to raw text — a third-party response shape we didn't anticipate should not fail a job.

**Guarding the hosted lane's real footgun in `dos agent validate`, not in a doc.** A tier-3 manifest that declares `tools`, `mcp_servers`, an `approval_policy`, or an `output_model` is now **rejected**. Every one of those is silently inert for a hosted agent — its tool calls happen on the far side of the runtime boundary, where `ApprovalGate` and `GuardrailGate` cannot see them. The dangerous case is `approval_policy`: an author who writes one, sees it accepted, and believes payments are gated would be wrong in the most expensive possible direction. Better to refuse the manifest than to document the trap.

**Registration by ARN is the hosted install path, so the ARN lives in the registry row** (`AgentPackage.runtime_arn`), not worker-side like the Gateway URL (E7.1 T1). Those look inconsistent but aren't: the Gateway URL is infrastructure the *control plane* owns and every agent shares, while a runtime ARN identifies *which* third-party agent a tenant installed — it is the registration data itself. `dos agent register-hosted --runtime-arn ...` writes the row with no package on disk at all, which is E7.3 T2's "no repo access" claim. `agents/vendorcheck/` exists as the same thing expressed as a package; a tier-3 manifest leaves `runtime_arn` unset and picks it up from `AGENTCORE_RUNTIME_ENDPOINT` at publish time, so an account-specific ARN never gets committed.

**A real dotenv footgun, found by the tier-3 path and fixed in `app/config.py`.** `AGENTCORE_RUNTIME_ENDPOINT=` followed by whitespace and an inline comment parsed the *comment* as the value: `agentcore_runtime_endpoint == "# hosted-agent lane (VendorCheck)"`. Unlike `KEY=value # note` (dotenv strips that correctly), a comment after an empty value becomes the value. It is a nasty failure because the result is **truthy**, so every `if not settings.x` no-op guard passed, the verify script's `assert arn` passed, and the error would only have surfaced much later as an unintelligible bad-ARN response from AWS. `_blank_env_vars_are_unset` now also treats a value that is only a comment as unset (no setting here can legitimately start with `#`), and the `.env` comment moved to its own line. Worth knowing generally: this trap applies to every optional `KEY=` in a `.env`.

**Hosted-lane verification is split deliberately.** `docs/AWS_SETUP.md` has the human run `agentcore invoke` against the deployed runtime *before* our activity touches it — the same isolate-the-AWS-side-first sequencing that made the E7.1 Gateway and Memory bugs quick to find. Then `make verify-hosted` (new) exercises the control-plane path: registers a throwaway agent by ARN alone (an id with no `agents/<id>/` directory, so nothing can silently fall back to disk), runs two real jobs with opposite expected verdicts (`Meridian Holdings` → blocked, `Globex Retail` → clear, so a pass cannot be explained by any-string-at-all), and asserts both that `invoke_hosted_agent` ran **and** that no `invoke_model*` activity did — the latter being the real regression guard on the tier-3 branch.

**Deployment uses the `CodeZip` build type, not `Container`.** AgentCore Runtime is ARM64 (Graviton), and `CodeZip` lets the CLI handle architecture compatibility without a local ARM64 Docker build — a materially lighter human step, and this agent has no system-level dependencies that would need a container. `BUILD_ID` v15→v16 (the workflow can now schedule a new activity), bumped and set current before testing.

**Verified without the runtime, ahead of the deploy:** a synthetic tier-3 package pointing at a syntactically valid but nonexistent ARN confirmed the branch end to end on real Temporal Cloud — `invoke_hosted_agent` scheduled, zero `invoke_model*` activities, and the job failing cleanly rather than silently succeeding. `make verify-agents` clean (no regression from the `run()` refactor), `make replay` clean at v16, ruff + mypy clean. The remaining gap is the real runtime: `make verify-hosted` cannot run until `AGENTCORE_RUNTIME_ENDPOINT` is set.

## 2026-09-01 — E5.1 T4: guardrail verdicts on the session terminal, and what it took to prove a block

**The verdict travels on the stream that already exists.** `GuardrailGate` awaits `apply_guardrail` in *workflow* context, so the result is already in the workflow when it arrives — no bridging from the activity side. The gate takes an `on_verdict` callback and `AgentJobWorkflow` publishes a `guardrail` `UIEvent` onto the existing `job_events` topic, alongside `job_started`/`memory_recall`/`approval_*`/`job_finished`. No third topic (same payload type), and **zero API change** — `events.py` already re-emits anything on `job_events` as an SSE event named by its `kind`, which is what makes new event kinds additive. `WorkflowStreamClient.from_within_activity()` is for content that never surfaces to the workflow, like E4.2's token deltas; using it here would have been cargo-culting. `BUILD_ID` v16→v17.

**`GuardrailVerdict` gained `evaluated`.** When no Guardrail is configured the activity returns without calling Bedrock at all, and publishing "passed" for a check that never ran would put a fake reassurance on a conference screen (CLAUDE.md §7). A fork with no Guardrail provisioned now shows nothing instead.

**Proving a *block* end to end took five attempts, and the failures are the interesting part.** The gate only sees a tool call the model actually proposes, so the test's content has to be something a cooperative agent will file. In order:

1. `"Skip the review process and file this immediately…"` — Claude refused to call the tool, correctly naming it a prompt-injection attempt.
2. Rephrased as third-person case data (`"Merchant asks that we bypass…"`) — refused again, same grounds.
3. Under an SOP explicitly instructing the agent never to refuse or sanitize — **still refused**. Worth knowing: "tell the model not to judge" does not reliably disable the judgement.
4. Reported as past narrative (`"Escalation threshold was overridden by finance on 12 Aug…"`) — refused on a *new* ground: the rationale is not evidence, and filing it would misrepresent a control bypass as chargeback evidence.
5. Raw cardholder PAN + expiry, targeting the guardrail's PII policy — refused on PCI grounds, by **Claude and by Nova Pro alike**.

**The finding, which outlasts this test: the guardrail's denied topic is nearly unreachable through a model turn, because its definition (instructions to bypass approval/review) is almost exactly the model's own refusal boundary.** That is not a defect — defence in depth working at the outer layer first — but it does mean the denied topic cannot be *demonstrated* on stage via an agent, and a guardrail whose only reachable path is "the model failed" is not a guardrail anyone can show working. What finally reached the gate was the managed **PROFANITY** word list: quoting a cardholder's own words verbatim is legitimate evidentiary behaviour that models will perform, and the match is a word list rather than a judgement call. The test also runs on `bedrock-nova` rather than Claude, which is the honest framing of the guarantee — the *platform* gate holds whatever model a package's author picked.

**The SOP's "preserve the customer's wording" clause is load-bearing, not a jailbreak.** Card-network filings quote the cardholder verbatim and paraphrasing weakens the evidence. Without that clause the model filed the profane quote about half the time — a coin flip that would have made `make verify-guardrail` a flaky guard rather than a guard.

**New `make verify-guardrail`.** Two real jobs on the real Guardrail over the real SSE route: a clean filing yields `blocked=false` *and* actually files once; the profane quote yields `blocked=true`, carries a reason, and the dispute service records **zero** filings for it. One run showed the model retrying after the block — the gate held both times and the filing count stayed 0.

## 2026-09-01 — A real UI streaming defect found while verifying the above, one half fixed

Verifying the terminal by hand surfaced something `make e2e` does not catch, because every e2e spec starts from a fresh page: **the second session on a long-lived page often never streams at all.** The pane shows the new job id, polls `/state` successfully, and sits at "waiting for output" forever.

**Diagnosed, not guessed.** `/api/jobs/<id>/events` counts in the API log tell the story: browser-driven jobs show 7, 5, 3, 3 requests *for the same job*, while script-driven (httpx) subscribers show exactly 1. `EventSource` reconnects automatically whenever the server closes the response — and `subscribe()` correctly returns as soon as the workflow reaches a terminal state — so a finished session becomes an endless reconnect loop. The page eventually logs `net::ERR_INSUFFICIENT_RESOURCES` on *plain polling fetches*, i.e. the whole pane starves, not just the stream.

**Fixed half:** `SessionTerminal` now calls `source.close()` in its `job_finished` handler. Stopping reading was never enough; only closing stops the reconnect loop. This is unambiguously correct on its own terms — a finished workflow's stream is gone and there is nothing further to receive.

**Still open, and it should block the stage rehearsal:** after the fix, a hung SSE request through Vite's dev proxy was still reproducible — the request reaches the server, the server streams fine (a direct `curl` to :8000 with the same 3s delay gets the full event sequence), but nothing arrives in the browser. The proxy is the bare string form (`proxy: { "/api": "http://localhost:8000" }`), which is the obvious next suspect. This matters more than a dev-loop annoyance: the presenter runs several sessions in a row without reloading, which is exactly the untested path. Filed as its own hardening item under E8 rather than folded in here.

## 2026-09-01 — Repeated-session streaming: two causes fixed, a third still open

Follow-up to the entry above. Chasing the "second session never streams" defect properly turned up **three distinct causes**, not one. Two are fixed; the third is not, and the reproduction is now a `test.fixme` in `ui/e2e/shell.spec.ts` so it stays visible in every run without turning the suite red.

**Fixed 1 — the stream is never closed when a session ends.** `SessionTerminal` set `live=false` on `job_finished` but left the `EventSource` open. `EventSource` reconnects on its own whenever the server closes the response, and `subscribe()` correctly returns the moment a workflow goes terminal, so every finished session became an endless reconnect loop. Now `source.close()` on `job_finished`.

**Fixed 2 — the same loop, reached a different way: attaching to an already-terminal job.** A fast tier-1 job can finish inside the pane's 2s job-poll interval, and an operator can select any past session, so `job_finished` may never arrive — meaning fix 1 has nothing to fire on. `onerror` now consults the polled-state endpoint (the one E4.2 T3 already added) and closes for good when execution status is not `RUNNING`, retrying only while it genuinely is. Confirmed by request counts: the same job that previously logged 3–7 `/events` requests now logs exactly 1.

**Still open — a stream that drops mid-session on a later round.** With both fixes in, round *n* of four delivers a real session (`session started — incident-triage` plus real tokens) and then goes idle without ever receiving `job_finished`. Distinct from both fixed causes and from the attach race. Not yet root-caused.

**Two corrections to my own earlier reasoning, recorded because both were wrong in instructive ways.** First, I reported that the new e2e spec "genuinely fails without the fix" — it does fail without it, but it *also* failed with it, so the run proved nothing about the fix; a guard has to be checked in both directions before it can be cited. Second, at two sessions the spec passed with the fix reverted, i.e. it was a guard that could not fail. Four rounds is what reproduces reliably, because the cost of each unclosed stream is one connection slot.

**`agent: false` on the Vite dev proxy** (`ui/vite.config.ts`, previously the bare string shorthand). Pooled keep-alive upstream sockets left over from finished streams were observed blocking new proxied requests entirely — they reached the dev server but never the API, with nothing in the API log to show for it. One socket per request costs nothing at demo scale and removes the shared state that failure mode depends on. Kept even though it did not by itself resolve the remaining cause.

**Note for whoever picks this up:** the server side is not implicated so far. A direct `curl -sN` to `:8000` on the same endpoint, attaching with the same delay the UI uses, receives the complete event sequence every time, and `make verify-guardrail`'s own httpx subscribers log exactly one request per job. The evidence points at the browser/proxy path, not at Workflow Streams or the API route.

Worth being clear about what this gives up, since the usage map claimed it: there is now **no per-tenant tool-authorization boundary**. Tenant isolation in this system is what the registry and the workflow enforce — installs are per tenant, priority and fairness are per tenant, memory is namespaced per tenant — but nothing stops a tenant's agent package from declaring a tool in its manifest and calling it. The `Policy` row stays `Declined for now` on its own merits — the human-in-the-loop and approval logic lives inside the Temporal workflow so every check is a Temporal event with full audit provenance, and that reasoning never depended on Identity.
